**I-01 — Important: the one-shot reservation is not exclusive.**

Location: `invoke.sh:32`, `invoke.sh:41`, `invoke.sh:50`, `invoke.sh:55` (relevant spans 30–45 and 48–57).

The script checks that the log is empty, performs several other preconditions, and only then appends a start row. No atomic claim, exclusive creation, or lock connects the empty-log predicate to launch. Two starts can both observe an absent/empty log and the original run-directory census, both append start rows, and both execute the retained solve. Both source checks can succeed: result directories and the journal are outside the verified source scope. The output redirects at line 57 target the same filenames and can overwrite/intermix the captures; line 60 can then select whichever journal row happens to be last.

Independent evidence is the static interleaving A/check-log, B/check-log, A/check-runs, B/check-runs, A/append, B/append, A/launch, B/launch. No concurrency experiment was run. This violates handoff obligation 3 and authorization-request lines 34–42: one authorization can produce two solves and no longer has unambiguous per-invocation captures. An exclusive persistent claim must precede launch; the current sequential check is not that predicate.

**I-02 — Important: failure to retain the start or completion records does not stop or fail the invocation.**

Location: `invoke.sh:8`, `invoke.sh:27`, `invoke.sh:50`, `invoke.sh:61`, `invoke.sh:72`, `invoke.sh:76`.

The shell enables only `set -u`. It does not inspect the exit status of directory creation, the start append, the completion append, or retained-file collection. For a concrete counterexample, an existing empty log file that is unwritable can satisfy line 32 while the surrounding directory and stdout/stderr files remain writable. The start append fails, but line 55 still launches. The same problem after a successful tool run allows recording/hash failures to be followed by `exit $rc` with `rc=0`. The `sha256sum | cut` helper also does not propagate the first pipeline command's failure reliably into a checked status.

Consequences: work can begin without its durable consumed-authorization record, and a successful exit can be reported despite missing invocation evidence. A pre-output-directory failure after a lost start record leaves neither of the script's later retry barriers established. This is a static failure-path conclusion, not a claim that the observed rehearsal lost records. The observed successful rehearsal does not exercise these paths. Required recording operations need explicit successful outcomes before launch and before reporting capture completion; a shell-wide errexit change alone would not define correct failure retention.
